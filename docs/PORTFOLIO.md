# 차곡

후불 거래의 청구와 입금을 관리하는 미수금 확인 서비스입니다. 비슷한 입금자명이나 금액을 연결 후보로 보여주고, 사용자가 근거와 현재 잔액을 확인한 뒤 연결을 확정하도록 만들었습니다.

## 사용 흐름

청구·입금 등록 → 연결 후보 조회 → 연결 금액 검토 → 확정 → 미수 확인 → 취소

청구 100,000원에 입금 40,000원을 연결하면 미수는 60,000원이 됩니다. 나머지 60,000원을 연결하면 0원이 되고, 두 번째 연결을 취소하면 60,000원으로 복구됩니다.

## 설계에서 다룬 문제

- 동시에 같은 입금에 요청이 들어와도 가용액을 넘지 않도록 잠금과 잔액 재검사를 적용했습니다.
- 응답을 받지 못한 요청을 다시 보내도 같은 배분이 중복 저장되지 않도록 요청 키와 결과를 보관합니다.
- 연결을 취소해도 청구·입금 원본과 확정 이력이 남도록 취소 기록을 분리했습니다.

구현 위치와 처리 방식은 [아키텍처](architecture.md), 테이블 관계는 [ERD](receivables-erd.md)에 정리했습니다.

## AI 에이전트 활용 과정

AI에 구현을 맡기기 전에 업무 규칙, 작업 범위와 완료 기준을 지시했습니다. 총괄 에이전트가 하위 작업을 나누고 결과를 모으도록 운영했고, 진행 결과를 바탕으로 우선순위와 수정 방향을 정했습니다.

| 제가 지시한 내용 | 에이전트가 수행한 작업 |
| --- | --- |
| 기존 코드를 점검하고 재사용, FREE MVP 우선 | 환경·코드 분석 후 단계별로 기존 프로젝트 확장 |
| 금액 계산은 Java, AI는 조회만 허용 | 금융 계산·확정을 서버에 유지하고 읽기 경계 분리 |
| 분석·개발·검토 역할 분담, 동시에 최대 2개 | 필요한 작업만 병렬 처리하고 구현 담당과 별도 검토 |
| 문서는 경량 모델, 코딩은 Sol 수준 사용 | 작업별 모델 선택 기준을 작업 규칙에 기록 |
| 실제 DB·브라우저 검증, 실패를 숨기지 않기 | 테스트·화면 검증 후 결함 수정과 재검증 |

### 실제로 내린 지시

- “금액 계산은 기존 Java 로직을 사용한다.”
- “하위 에이전트는 필요한 경우에만 실행하고 동시 실행은 최대 2개로 제한하세요.”
- “자동 테스트에서는 기본적으로 실제 유료 API 호출 금지”
- “실제 브라우저에서 렌더링된 화면과 주요 상호작용을 확인한다.”

이 기준에 따라 한 기능씩 구현하고 검토 결과를 받아 다음 작업을 진행했습니다. 서비스 목표를 미수금 확인으로 좁히고, 이후에는 포트폴리오 완성과 앱인토스 검토를 우선하도록 순서를 바꿨습니다. 문서·영상의 반복 설명도 줄이도록 개선을 요청했습니다.

### 결과를 어떻게 확인했는가

에이전트가 실제 PostgreSQL과 브라우저 검증을 실행하고 결과·화면·재현 스크립트를 남겼습니다. 개발 담당과 별도의 검토에서 다음 문제가 발견돼 수정됐습니다.

- 공백만 수정해도 재전송 키가 바뀌는 문제: 정규화한 입력으로 키를 유지하도록 변경. 실제 저장 후 오류 응답을 받는 상황을 재현하고, 같은 키로 재시도해 입금이 한 건만 남는지 확인.
- 이전 조회가 늦게 도착해 새 후보를 덮는 문제: 조회 상태를 제어하고 경합을 다시 검사.
- 취소 요청 중 화면 이동으로 키가 사라지는 문제: 요청 중 탐색을 잠그고 사업체 단위로 키와 초안을 보관.

업무 문제·제약·우선순위와 개선 요청은 제가 정했고, 분석·구현·검증 실행은 에이전트를 활용했습니다. 수정 사례의 기술 근거는 [기본 화면 검토](receivables-mobile-core-review.md)와 [입금 연결 검토](receivables-mobile-matching-review.md)에 있습니다.
