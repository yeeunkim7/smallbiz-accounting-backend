# 차곡 — 입출금 대사에서 미수금 확인으로

## 개발 배경

기존 시스템은 업무상 예정 금액과 은행 입출금을 날짜별로 대사했습니다. 이 구조는 하루의 차이를 찾는 데 사용할 수 있지만, 합계가 같다는 사실만으로 개별 청구의 지급 여부를 판단할 수는 없습니다. 부분 입금과 여러 청구를 합친 입금에서는 청구별 남은 금액과 연결 이력이 필요합니다.

소규모 사업자의 미수금·입금 확인을 목표로 기존 프로젝트를 확장했습니다. Java/Spring Boot, PostgreSQL, Flyway와 기존 대사 API·원본을 보존하고, 사업체별 청구·입금·배분 도메인과 Expo 화면을 추가했습니다. 실제 고객 수요와 공개 서비스 운영은 아직 검증하지 않았습니다.

## 핵심 업무 흐름

청구 등록 → 입금 등록 → 연결 후보 조회 → 사용자 검토 → 확정 → 미수금 조회 → 필요 시 취소

| 단계 | 생성·변경되는 데이터 |
| --- | --- |
| 청구·입금 등록 | 사업체 소유 청구와 지급기한, 은행 CSV 또는 직접 입력 입금을 저장한다. 입금 등록만으로 미수를 줄이지 않는다. |
| 후보 조회 | 당시 원본·잔액을 기준으로 실행 결과를 저장한다. 정상 완료 실행은 이용량에 반영하며 배분은 생성하지 않는다. |
| 사용자 검토·확정 | 현재 잔액을 확인하고 배분 batch·line·감사를 저장한다. 확정 트랜잭션에서 잔액을 다시 검사한다. |
| 미수 조회 | 청구 원금에서 유효한 배분을 제외한다. 미배분 입금과 지급기한 초과 잔액은 따로 조회한다. |
| 취소 | 사유·취소 기록을 추가하고 조회 시 상태·버전을 파생한다. 원본과 기존 배분 line을 보존하며 조회 잔액이 복원된다. |

예를 들어 청구 100,000원에 40,000원을 연결하면 미수는 60,000원이다. 남은 금액을 연결하면 0원, 두 번째 연결을 취소하면 다시 60,000원이다. [실제 시연](demo/receivables-demo.mp4)

## 주요 기술적 의사결정

**기존 대사와 미수금 도메인을 분리했습니다.** 예정 현금흐름을 채권으로 재해석하면 기존 검토 상태와 신규 지급 상태가 섞입니다. 기존 데이터의 의미를 유지하라는 개발자 지시에 따라 별도 tenant 소유 모델을 추가했습니다. 기존 자료 자동 이관을 제공하지 않는 비용이 있습니다. 구체 테이블 설계는 에이전트 구현에서 확인되며 개발자의 직접 DDL 결정으로 표현하지 않습니다.

**후보와 확정을 분리하고, 확정 시 잔액을 재검사합니다.** 사용자 검토·확정은 개발자가 지정한 업무 흐름입니다. 배분은 다대다 line으로 부분·묶음·분할 입금을 표현합니다. 동시에 같은 입금을 사용하는 요청은 부모 행을 정해진 순서로 잠근 뒤 합산 잔액을 다시 검사합니다. 이 잠금 설계는 에이전트가 구현했으며 처리량 성능을 측정한 것은 아닙니다.

**성공 결과와 사용량을 같은 트랜잭션에서 저장합니다.** 성공한 실행만 집계한다는 요구에 대해, 초기 비동기 예약 제안을 제한된 동기식 트랜잭션으로 대체한 기록이 있습니다. 결과·사용량 이력·counter가 함께 저장되거나 롤백됩니다. 복구 구조는 단순해지지만 동시 실행이 월별 행에서 대기할 수 있습니다.

각 결정의 문제·대안·판단 주체·트레이드오프·구현과 검증은 [ADR 0002](adr/0002-receivables-decisions.md)에 정리했습니다. 인증 경계는 [ADR 0001](adr/0001-auth-tenant-ai-boundary.md), 실제 호출 흐름과 테이블 관계는 [아키텍처](architecture.md)와 [ERD](receivables-erd.md)를 기준으로 합니다.

## AI 에이전트 활용 과정

### Codex 선택과 역할 구성

기존 저장소의 코드·DB·테스트를 함께 확인하고 변경을 실행할 수 있는 작업 환경이 필요했습니다. Codex에서 저장소 분석, 파일 수정, 명령 실행과 Git 이력을 연결하고 하위 에이전트의 결과를 통합했습니다. 다른 도구와의 비교 실험이나 생산성 배수를 측정한 것은 아닙니다.

개발자는 서비스 목표, 업무 제약, 범위와 완료 기준을 지시했습니다. 총괄 에이전트는 기획·업무 분석, 자료조사, 디자인, 개발, 독립 검토 역할을 필요한 단계에 배분했습니다. 기획은 총괄과 분석이 함께 담당했고, 모든 역할을 상시 동시에 실행하지 않았습니다.

- 조사·분석은 대상 업무와 기존 데이터의 재사용 경계를 정리해 도메인·API 설계에 전달했습니다.
- 디자인은 등록부터 확인·확정까지의 흐름과 상태·금액·근거 표시 규칙을 정했습니다.
- 개발은 기능별 코드를 구현하고 테스트를 실행했습니다. 별도 검토 담당이 오류를 재현하고 수정 요구를 전달했습니다.
- 총괄은 수정·재검증 결과와 화면을 모아 보고하고 작업 기록을 유지했습니다.

### 실제 채택 과정과 한계

개발자는 기존 원본 보존, Java 금액 계산, 사람의 확정, FREE의 AI 호출 금지 등을 지정하고 서비스 목표와 우선순위를 조정했습니다. 사용량의 동기 트랜잭션, 부모 행 잠금 등 구체 구현은 에이전트의 설계·작업 기록으로 확인됩니다. 모든 세부 설계를 개발자가 직접 비교·승인했다고 말할 근거는 없습니다.

AI가 구현과 테스트 실행을 수행했으며, 독립 검토도 AI 에이전트의 검토입니다. 테스트 통과만으로 개발자의 코드 이해·최종 검토나 운영 안정성이 입증되지는 않습니다. 이번 정리를 계기로 주요 업무·DB·아키텍처 변경 전 사용자 결정을 받고, 구현 후 핵심 코드와 실행 결과를 개발자가 검토하는 절차를 [작업 규칙](../AGENTS.md)에 명시했습니다. 기존 기록에 소급해 승인을 붙이지 않습니다.

## 기술적 문제 해결 사례

### 1. 응답 유실 뒤 공백 수정이 중복 저장 위험으로 이어짐

서버는 저장했지만 클라이언트가 응답을 받지 못한 경우, 같은 키로 재요청해야 기존 결과를 받을 수 있습니다. 검토에서 공백만 수정해도 키가 초기화돼 같은 정규화 입력에 새 키를 보내는 문제가 발견됐습니다. 서버 입장에서는 다른 명령이므로 멱등성만으로 막을 수 없습니다.

[Registration.submit](../mobile/src/forms.tsx)에서 정규화한 payload를 만들고 [CommandKey.forPayload](../mobile/src/commands.ts)에 전달하도록 유지하며, 원시 입력 변경에 따른 키 초기화를 제거했습니다. 서버의 [ReceivablesService.createPayment / replayOrCreate](../backend-java/src/main/java/com/smallbiz/reconciliation/receivables/ReceivablesService.java)는 동일 키의 내용을 검증하고 저장 결과를 재사용합니다.

에이전트가 실제 PostgreSQL 저장 뒤 첫 응답을 503으로 바꿔 재현했습니다. 공백 수정 후 재시도해 동일 키와 입금 한 건을 확인했습니다. [독립 검토 기록](receivables-mobile-core-review.md) · [재현 스크립트](../scripts/verify-receivables-mobile-browser.py)

### 2. 늦은 조회 응답이 새 후보 결과를 덮는 경합

저장 결과 GET이 끝나기 전에 새 후보를 생성하면, 이전 GET이 늦게 도착해 최신 결과를 덮을 수 있었습니다. [LiveMatching.openRun / generate](../mobile/src/matching-screen.tsx)의 조회 상태와 생성 잠금을 연결해 읽는 동안 새 생성이 진행되지 않도록 수정했습니다.

별도 검토 에이전트가 GET 응답을 지연하는 화면 fixture로 생성 잠금을 확인했습니다. 이 검사는 UI 경합의 근거이며 실제 금융 계산의 증거와 구분합니다. 실제 서버 검증에서는 부분·묶음·분할 확정과 취소 후 잔액 복원을 별도로 확인했습니다. [독립 검토 기록](receivables-mobile-matching-review.md) · [실제 API 시나리오](RECEIVABLES_MOBILE_MATCHING.md)

## 현재 구현 상태

- **구현:** 계정·사업체 격리, 청구·입금 등록, CSV API·원본 추적, 규칙 후보, 수동 확정·취소·감사, 잔액·이용량, Expo 핵심 흐름.
- **검증 기록:** 2026-11-01 백엔드 186개, 클라이언트 13개, 실제 브라우저·API 연결 9개와 기본 화면 회귀 9개 통과. 별도 11개 UI fixture는 금융 계산 테스트에 합산하지 않습니다. 이번 문서 작업에서 재실행하지 않았습니다.
- **미검증·후속:** iPhone·Android 실기기, 모바일 CSV 화면, 공개 운영 보안·보존/삭제·계정 복구, 고객 파일럿, 앱인토스·스토어, 결제·구독. PRO AI 자산은 보존했지만 실제 모델 검증은 미완료이며 현재 FREE 흐름은 모델을 호출하지 않습니다.
- **개발자 확인 필요:** 세부 DB·잠금·사용량 설계의 유지 판단과 핵심 코드 이해·최종 검토 기록. 기존 AI 실행 결과와 구분해 앞으로 남깁니다.
