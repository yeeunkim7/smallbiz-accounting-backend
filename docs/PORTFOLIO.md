# 포트폴리오: 후불 청구의 입금 확인과 미수 관리

## 문제와 사용자 흐름

소규모 후불 사업자는 청구한 금액, 나눠 들어온 입금, 여러 청구를 한 번에 처리한 입금을 대조해 현재 남은 금액을 알아야 합니다. 단순히 이름·날짜·금액이 비슷한 행을 자동 연결하면 오배분이 잔액에 반영될 수 있습니다. 이 프로젝트는 후보와 근거를 보여주고, 사용자가 행과 금액을 검토한 다음 서버가 잔액 한도 안에서 확정하도록 구성했습니다.

대표 흐름은 거래처·청구·입금 등록(또는 tenant 은행 CSV 가져오기), 날짜·이름·금액 규칙 후보 생성, 후보·원본 근거 확인, 부분/묶음/분할 배분안 편집, 서버 현재 잔액 검토, 별도 확정, 잔액 및 감사 이력 확인, 사유를 입력한 취소입니다. 후보 생성은 저장된 시점의 snapshot이며 이후 원본이 바뀌어도 과거 실행 결과를 수정하지 않습니다. `GET` 잔액은 현재 상태이고 `asOf`는 현재 남은 금액 중 지급기한을 넘긴 부분을 분류하는 기준 날짜입니다. 과거 시점의 원장 재구성 기능을 뜻하지 않습니다.

실제 검증 시나리오는 합성된 청구 A 100,000원, 청구 B 50,000원, 입금 40,000원·60,000원·150,000원입니다. 기록된 Chromium/API 실행에서 40,000원 부분 배분 후 110,000원 미수, 40,000+60,000원 배분 후 50,000원 미수, 150,000원을 100,000/50,000원으로 나누어 배분 후 미수 0원을 확인했습니다. 각 취소가 원래 미수를 복원하고 감사 이력을 보존하는 것도 확인했습니다. 이 값은 자동 추론 성능이나 실거래 실적이 아니라 명시된 시나리오의 기능 결과입니다.

## 설계 판단

- **후보는 추천으로만 취급.** [MatchingService.java](../backend-java/src/main/java/com/smallbiz/reconciliation/receivables/matching/MatchingService.java)는 한 PostgreSQL statement snapshot으로 후보 근거와 당시 배분 상태를 읽어 불변 실행 결과를 저장합니다. 후보 부재는 누락된 파일/입금의 증거가 아니며, 클라이언트 후보 점수는 확정 금액이 아닙니다. 자동 배분이나 단순 총액 일치 방식은 이 흐름에서 사용하지 않습니다.
- **확정과 취소를 원본 위에 덮어쓰지 않음.** [AllocationService.java](../backend-java/src/main/java/com/smallbiz/reconciliation/receivables/allocation/AllocationService.java)는 결제·청구 부모를 일정한 순서로 잠그고 현재 가용액을 다시 검증한 뒤 batch, line, 감사 기록을 트랜잭션으로 저장합니다. 취소는 원 batch를 수정하는 대신 사유가 있는 취소 사실을 추가합니다. 동시 배분은 같은 부모 잠금과 재검증으로 초과를 막습니다.
- **명령 재생과 현재 상태를 구분.** 등록·배분 명령은 tenant 범위의 idempotency key와 요청 hash를 저장합니다. 같은 payload 재전송은 저장된 결과를 돌려주며, 다른 payload의 같은 키는 충돌입니다. [배분 상세 GET](RECEIVABLES_ALLOCATION.md)은 현재 상태를 다시 읽는 경로이고, 과거 confirm key의 응답은 최초 version snapshot일 수 있습니다. 앱은 확정/취소 후 상세 GET으로 현재 상태를 갱신합니다.
- **사용량은 성공 결과와 함께 기록.** [UsageService.java](../backend-java/src/main/java/com/smallbiz/reconciliation/receivables/matching/UsageService.java)와 매칭 실행은 run 결과·승인 월·고유 event·counter를 동기 트랜잭션으로 커밋합니다. 실패와 재생은 추가 차감하지 않습니다. 기본 FREE 10회는 검증 대상 설정 가설이고, STANDARD/PRO는 설정 전 0회입니다. 가격·구독·유료 entitlement는 구현하지 않았습니다.
- **기존 금융 데이터의 소유권을 추측하지 않음.** V8 이후 인증·tenant 테이블을 추가했지만 V1~V7 전역 행은 미할당 상태로 둡니다. 새 receivables 테이블은 `(tenant_id, id)` 외래 키와 tenant 범위 키로 경계를 강화합니다. 파일이 없다고 단정하거나 legacy 자료를 새 사용자에게 자동 귀속시키지 않습니다.

## 검증 결과의 범위

저장소의 마지막 기록 실행일은 2026-11-01입니다. 이 문서는 그 결과를 재실행했다고 주장하지 않습니다.

| 검증 묶음 | 마지막 기록 결과 | 의미 |
| --- | --- | --- |
| Java 백엔드 | 186 통과, 실패/오류/건너뜀 0 | 전용 테스트 DB의 백엔드 회귀·통합 테스트 |
| 모바일 클라이언트 | 13 통과, 타입 검사 및 웹 export 성공 | 앱 로직·타입 및 브라우저 번들 생성 |
| 실제 Chromium + Java API | 매칭 신규 9 + 코어 회귀 9 통과, 페이지 오류 0 | 실제 로컬 API와 격리 DB의 합성 tenant 흐름 |
| 독립 UI fixture | 11 통과 | 경합·불확실한 응답 등 별도 fixture 검토. 실제 금융 계산 검증과 다른 묶음 |

각 행은 서로 다른 검사 묶음이며 하나의 전체 테스트 합계처럼 더하지 않습니다. 브라우저의 실제 서버 흐름은 합성 데이터를 사용했고, 별도 UI fixture는 모의 응답을 사용했습니다. 개발 DB 보존 확인은 행 수 비교로 기록됐으며 데이터 바이트/내용 해시 동일성 확인은 아닙니다. 재현 절차와 화면은 [모바일 연결 검증 기록](RECEIVABLES_MOBILE_MATCHING.md)을 참조하세요.

## 남은 확인

공개 FREE 서비스 운영 전에는 개인정보 처리·접근 복구·보존 및 삭제·백업/복구·요청 제한·오류 관측·운영 권한을 점검해야 합니다. 모바일 CSV 화면, iOS/Android 실기기와 VoiceOver/TalkBack, 화면 확대, 앱인토스 서비스 적합성·SDK/API 계약과 정책, 앱 심사 및 배포는 미검증입니다. 실제 결제·구독, AI(PRO), 은행 API 연결, 돈 이동은 이 작업 범위가 아닙니다. 무료 한도 및 가격은 시장·운영 검증 전의 정책 가설입니다.

## 코드로 설명할 지점

| 질문 | 구현 근거 |
| --- | --- |
| 동시에 같은 입금을 배분하면? | AllocationService.confirm/cancel의 payment→invoice 정렬 잠금과 잔액 재검증, 초과 시 전체 rollback |
| 응답을 못 받았는데 다시 누르면? | ReceivablesService.replayOrCreate와 AllocationService의 command/audit 결과 재생, 앱 CommandKey canonical payload |
| 예전에 확정한 응답과 지금 상태가 다르면? | 불변 command snapshot과 GET 상세를 구분하고 모바일이 현재 상태를 재조회 |
| 무료 횟수가 경합하거나 실패하면? | MatchingService.create + UsageService.approve/complete의 동일 트랜잭션과 월 행 잠금, 결과/event/counter 원자성 |
| 은행 입금과 청구가 비슷하면 바로 연결하나? | MatchingService.sources/suggestions는 근거만 만들고 모바일의 현재 잔액 검토 뒤 사람이 별도 확정 |

AI 코딩 도구를 구현·문서·독립 검토 보조에 사용했습니다. 이 자료는 작성 방식이나 실사용 성과를 과장하기보다 저장소에서 확인할 설계 선택, 실행 근거와 미확인 범위를 설명합니다. 면접에서는 각 선택의 이유와 테스트가 막는 오류를 실제 코드로 설명하는 것을 목표로 합니다.
