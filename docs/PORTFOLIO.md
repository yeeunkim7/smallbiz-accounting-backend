# 차곡 — 청구와 입금을 연결하는 미수금 확인 서비스

차곡은 소규모 사업자가 청구 내역과 은행 입금을 연결하고, 아직 받지 못한 금액을 확인하는 서비스입니다. 기존 Java 입출금 대사 시스템을 보존하면서 청구별 미수금 관리로 확장했습니다. Codex의 총괄·하위 에이전트를 활용해 개발했고, 이후 개발자 PC에서 Hermes 조회 도구를 실제 Java API에 연결했습니다.

[발표 PPT 5장](portfolio/chagok-project.pptx) · [발표 PDF](portfolio/chagok-project.pdf) · [시연 영상](demo/receivables-demo.mp4)

## 어떤 문제를 풀었나

하루 청구 합계와 입금 합계가 같아도 어떤 청구가 지급됐는지는 알 수 없습니다. 한 청구를 나눠 입금하거나 여러 청구를 한 번에 입금하면 연결 관계와 남은 금액을 따로 관리해야 합니다.

차곡은 **청구 등록 → 입금 등록 → 연결 후보 조회 → 사용자 확정 → 미수금 조회**를 지원합니다. 청구 100,000원에 입금 40,000원을 등록해도 미수는 그대로입니다. 사용자가 연결을 확정하면 미수 60,000원이 됩니다. 연결 취소는 원본 입금을 지우지 않고 취소 사유와 이력을 남깁니다.

구현 범위는 거래처·청구·입금 등록, 은행 CSV 가져오기 API와 중복·출처 추적, 부분·묶음·분할 연결, 취소·감사 이력, 사업체별 접근 제어, 성공한 후보 실행의 월별 사용량입니다. 앱 핵심 흐름은 브라우저에서 확인했으며 실제 고객 파일럿과 모바일 실기기 검증은 남아 있습니다.

## 왜 Codex를 사용했나

새로 만든 작은 예제가 아니라 기존 코드와 DB를 유지하며 기능을 확장해야 했습니다. 코드 분석부터 파일 수정, 테스트 실행, Git 기록까지 한 작업 공간에서 이어가고, 역할별 에이전트의 결과를 통합할 수 있다는 점 때문에 Codex를 활용했습니다.

처음부터 전체 재개발을 맡기지 않고 기존 구현·테스트를 확인하게 했습니다. 그다음 업무 규칙을 정하고 기능 단위로 구현·검토·수정을 반복했습니다. 다른 도구보다 빠르다는 비교 실험이나 개발 시간 절감률은 측정하지 않았습니다.

## 에이전트를 어떻게 구성했나

개발자는 목표와 업무 규칙, 우선순위와 완료 기준을 정했습니다. 총괄 에이전트에는 작업 분배, 선행 결과 연결, 수정 파일 충돌 방지와 결과 통합을 맡겼습니다.

| 역할 | 맡긴 일 | 다음 작업으로 넘긴 결과 |
| --- | --- | --- |
| 기획·업무 분석 | 기존 코드·DB와 새 미수금 업무의 차이 확인 | 재사용 범위, 도메인·API 계약 |
| 자료조사 | 사용자 문제와 유사·대체 서비스 비교 | 대상 고객 가설, FREE 우선 범위 |
| 디자인 | 등록·확인·확정 흐름과 상태 표현 | 화면 구성, 금액·오류·빈 화면 규칙 |
| 개발 | 백엔드·모바일을 기능별로 구현 | 변경 코드, 테스트·실행 결과 |
| 독립 검토 | 구현 담당과 별도로 코드·실패 상황 확인 | 결함과 재현 방법, 수정 후 검증 |

조사와 코드 분석처럼 독립적인 작업은 병행하고, 화면 구현은 도메인과 API 결과를 받은 뒤 진행했습니다. 역할은 필요한 단계에 투입했으며, 동시 하위 에이전트는 최대 2개로 제한했습니다.

제가 지정한 주요 기준은 기존 원본 보존, Java 금액 계산, 사용자의 확정, FREE의 AI 호출 금지였습니다. 구체 DDL·잠금·트랜잭션 구현에는 에이전트를 활용했습니다. 개발 규칙은 [AGENTS.md](../AGENTS.md), 결정 근거는 [ADR](adr/0002-receivables-decisions.md)에 남겼습니다.

## 실행 아키텍처와 기술 스택

제품은 **Expo 화면 → Spring Boot API → PostgreSQL**로 동작합니다. 신규 미수금 모듈은 Controller → Service → JdbcTemplate(SQL) 구조이고, 기존 대사 모듈의 JPA Repository는 유지했습니다.

| 영역 | 사용 기술 | 적용 위치 |
| --- | --- | --- |
| 백엔드 | Java 21, Spring Boot 4.1.1, Spring Security | 인증·사업체 권한, 등록·확정·잔액 API |
| 데이터 접근 | Spring JDBC/JdbcTemplate, JPA | 신규 미수금 SQL / 기존 대사 모듈 |
| DB·빌드 | PostgreSQL 17, Flyway V1–V13, Gradle Wrapper | 원본·배분·감사, 스키마 변경, 빌드 |
| 화면 | TypeScript, React Native 0.88, Expo 58, React 19 | 모바일 공통 코드, 브라우저 실행·검증 |
| 검증 | JUnit, Spring 통합 테스트, PostgreSQL, Playwright, Python unittest | 금액·권한·재시도·브라우저·조회 도구 |
| AI 개발·실습 | Codex, Hermes Agent 0.22.6, Python | 개발 역할 분담 / 로컬 읽기 도구 연결 |
| 개발 환경 | Git/GitHub, Windows + WSL2 Ubuntu | 변경 이력, 개인 PC 실행 환경 |

배분 확정은 한 DB 트랜잭션에서 요청 키 확인, 부모 행 잠금, 잔액 재검사, 배분·감사 저장을 처리합니다. 같은 키의 재시도는 저장된 결과를 재사용하고, 다른 키의 동시 배분은 잠금 후 남은 금액을 다시 확인합니다. 성공한 후보 실행만 이용량에 반영합니다.

Hermes 실습은 제품 밖의 별도 경로입니다. **질문 → Hermes → Python 조회 도구 → 인증된 Java GET → DB → 요약 답변**으로 이어집니다. 도구에는 날짜만 입력하고 주소·사업체·인증 정보는 모델이 바꾸지 못하게 했습니다. 금액은 서버 응답을 그대로 전달합니다. [아키텍처](architecture.md) · [ERD](receivables-erd.md) · [플러그인 소스](../examples/hermes/chagok-local-api)

## 검토가 수정으로 이어진 사례

### 저장은 됐는데 응답을 못 받은 경우

서버 저장 뒤 응답이 끊기면 저장 성공 여부를 클라이언트가 알 수 없습니다. 같은 키로 재시도해야 하는데, 검토에서 입력의 공백만 바꿔도 키가 초기화되는 문제가 발견됐습니다.

에이전트가 정규화한 내용이 같으면 같은 키를 유지하도록 수정하고, 실제 DB 저장 뒤 응답만 503으로 바꾸어 재현했습니다. 재시도 후 입금은 1건이었습니다. 저는 이 사례를 통해 멱등성과 동시성 제어가 다른 문제임을 학습했고, 내용이 다른 재요청을 거절한 뒤 잔액이 유지되는 검증 위치와 기대값을 설명했습니다.

[Registration.submit](../mobile/src/forms.tsx) · [CommandKey.forPayload](../mobile/src/commands.ts) · [재현 기록](receivables-mobile-core-review.md)

### 늦게 도착한 조회가 새 결과를 덮는 경우

이전 후보 결과 GET이 늦게 도착해 새 결과를 덮을 수 있었습니다. 조회 중 새 생성을 잠그도록 수정하고, 별도 검토에서 응답 지연으로 확인했습니다. UI 경합 검증과 실제 금액 검증은 구분해 기록했습니다. [검토 기록](receivables-mobile-matching-review.md)

## 직접 실행하며 확인한 결과

2026-11-04 개인 PC에서 WSL·Java 21·PostgreSQL 17 환경을 구성했습니다. 개발·테스트 DB와 계정을 나누고 교차 접속이 차단된 것을 확인했습니다. Windows 마운트 경로의 빌드 권한 오류는 기존 폴더를 보존한 채 Linux 홈에 별도 복제해 해결했습니다.

| 확인 내용 | 결과와 근거 |
| --- | --- |
| 백엔드 전체 테스트 | 사용자 PC XML 집계 186개, 실패·오류·스킵 0 |
| DB 초기화 | 사용자 시작 로그에서 Flyway V1–V13 적용과 서버 시작 확인 |
| 인증 경계 | health 200, 미인증 auth/me 401 |
| 실제 Java 조회 | 합성 청구 100,000 / 확정 배분 40,000 / 미수 60,000원 |
| 실제 Hermes 도구 호출 | 사용자가 실행 표시를 확인하고 금액·건수·API 근거를 포함한 답변 공유 |
| 잘못된 날짜 | INVALID_DATE 직접 함수 검사 통과 |
| 인증·접속 오류 | 모의 401·연결 실패를 AUTH_REQUIRED / UPSTREAM_UNAVAILABLE로 구분 |

Hermes가 조회한 것은 **현재 원장 요약**입니다. asOf는 연체 판정 기준일이며 특정 날짜 거래나 과거 잔액 조회가 아닙니다. 개별 거래 원본까지 조회했다고 표현하지 않았습니다. 이 기록은 사용자 제공 실행 로그·화면·확인에 근거하며, PRO 제품의 AI 출시 검증을 뜻하지 않습니다.

기존 에이전트 검증 기록은 2026-11-01 백엔드 186개·클라이언트 13개·실제 브라우저 9+9개입니다. 새 플러그인은 클라우드에서 오프라인 단위 10개를 검사했습니다. 이 수치를 하나의 테스트 실행으로 합산하지 않습니다. [학습·실행 기록](PORTFOLIO_LEARNING.md)

## 무엇을 배웠나

- **업무 규칙을 먼저 정해야 했습니다.** 입금 등록과 청구에 대한 확정 배분은 다릅니다. 합계가 맞는 것과 개별 청구가 지급된 것도 구분해야 합니다.
- **실패 뒤 데이터까지 확인해야 했습니다.** 오류 응답만 검사하지 않고 청구 미수와 미배분 입금이 그대로인지 확인했습니다. 안내를 받아 입금 잔액 assertion 한 줄을 작성했고, 파일 반영·실행은 에이전트가 수행했습니다.
- **도구의 권한과 응답 범위가 답변의 근거가 됩니다.** Hermes 예제를 직접 설치하고 거래처 필드를 추가했습니다. 이후 실제 Java GET을 연결해 자료 없음과 조회 실패, 현재 잔액과 과거 잔액을 구분하는 과정을 확인했습니다.
- **AI에게 맡긴 일도 검증 기준이 필요했습니다.** 역할과 산출물, 완료 조건을 나누고 구현 담당과 검토 담당을 분리했습니다. 이제는 핵심 코드를 직접 설명하고 변경 근거를 검토하는 범위를 늘리고 있습니다.

설치·명령 실행·예제 적용·필드 수정은 직접 수행했고, 코드 예제와 절차 안내는 에이전트의 도움을 받았습니다. 핵심 코드 전체를 독자 설계·구현했다고 표현하지 않습니다.

## 남은 범위

Docker 설치·배포는 현재 보류했습니다. 다음은 핵심 코드 설명과 개발자 검토 기록, iPhone·Android 실기기, 공개 운영 보안과 사용자 파일럿입니다. 앱인토스·스토어·구독은 후속 검토 대상입니다. FREE 업무는 AI를 호출하지 않으며, 로컬 Hermes 실습으로 제품의 PRO AI가 개방되지는 않습니다.
