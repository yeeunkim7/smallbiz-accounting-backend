# 차곡

후불 거래의 청구와 입금을 관리하는 미수금 확인 서비스입니다. 비슷한 입금자명이나 금액을 연결 후보로 보여주고, 사용자가 근거와 현재 잔액을 확인한 뒤 연결을 확정하도록 만들었습니다.

## 사용 흐름

청구·입금 등록 → 연결 후보 조회 → 연결 금액 검토 → 확정 → 미수 확인 → 취소

청구 100,000원에 입금 40,000원을 연결하면 미수는 60,000원이 됩니다. 나머지 60,000원을 연결하면 0원이 되고, 두 번째 연결을 취소하면 60,000원으로 복구됩니다.

## 설계에서 다룬 문제

- 동시에 같은 입금에 요청이 들어와도 가용액을 넘지 않도록 잠금과 잔액 재검사를 적용했습니다.
- 응답을 받지 못한 요청을 다시 보내도 같은 배분이 중복 저장되지 않도록 요청 키와 결과를 보관합니다.
- 연결을 취소해도 청구·입금 원본과 확정 이력이 남도록 취소 기록을 분리했습니다.

구현 위치와 처리 방식은 [아키텍처](architecture.md), 테이블 관계는 [ERD](receivables-erd.md)에 정리했습니다.

## AI 에이전트 활용 과정

### Codex를 선택한 이유

이 프로젝트는 기존 Java/Spring Boot 입출금 대사 시스템을 분석하고, 원본 데이터와 계산 규칙을 유지하면서 미수금 관리까지 확장하는 작업이었습니다. 저장소의 코드·DB 스키마·테스트를 함께 확인하고, 변경 사항을 실제로 실행한 뒤 Git 이력으로 남길 수 있는 개발 환경이 필요했습니다.

Codex는 같은 작업 공간에서 코드 분석, 파일 수정, 명령 실행, 테스트와 Git 작업을 이어갈 수 있었습니다. 여기에 하위 에이전트를 역할별로 나누어 총괄이 결과를 통합하도록 구성했습니다. **기존 시스템을 이해하는 단계부터 구현과 검증까지 연결할 수 있다는 점**이 이 프로젝트에서 Codex를 활용한 핵심 이유입니다.

### 제가 정한 기준과 에이전트 구성

저는 서비스가 해결할 문제, 구현 범위, 업무 규칙과 완료 기준을 정했습니다. 총괄 에이전트에는 단계마다 조사·분석 결과를 반영해 다음 작업을 배분하고, 충돌하는 요구사항과 변경 파일을 조정하도록 지시했습니다.

| 역할 | 맡긴 일 | 다음 작업에 전달할 결과 |
| --- | --- | --- |
| 총괄 | 범위·우선순위 관리, 작업 분배, 결과 통합 | 기능별 계획, 담당 범위, 검증 상태와 남은 문제 |
| 기획·업무 분석 | 기존 대사 흐름과 DB 구조 분석, 미수금 도메인과의 차이 정리 | 재사용할 기능, 새 도메인 경계, API·데이터 설계 |
| 자료조사 | 회계·정산 서비스와 수작업 대안 조사 | 대상 고객 가설, 핵심 업무 흐름, 우선 구현 범위 |
| 디자인 | 등록→후보 확인→확정→잔액 조회 흐름 설계 | 화면 구조, 상태·문구·금액 표시 규칙, 렌더링 검토 |
| 개발 | 기능 단위 백엔드·모바일 구현 | 코드, 마이그레이션, 테스트와 실행 결과 |
| 독립 검토·테스트 | 구현 담당과 별도로 업무 규칙·경합·오류 상황 점검 | 재현 조건, 수정 요구, 재검증 결과 |

역할은 작업의 책임을 나누는 기준으로 사용했습니다. 모든 역할을 상시 실행하지 않고, 기획은 총괄·업무 분석과 함께 수행하며 필요한 단계에 담당 에이전트를 투입했습니다. 구현 담당과 검토 담당을 분리해 구현 시 놓친 가정을 다시 확인하도록 했습니다.

### 작업을 진행한 방식

1. **현재 상태를 먼저 확인했습니다.** Git 상태, 기존 소스와 DB 스키마, 개발·테스트 DB 분리 및 기존 테스트 결과를 확인하도록 했습니다. 재사용할 부분과 변경할 부분을 정한 뒤 개발을 시작했습니다.
2. **조사와 코드 분석을 병행했습니다.** 사용자 업무와 기존 구조를 함께 검토하고, 입출금 예정 데이터와 청구·미수금의 의미를 구분했습니다. 기존 `business_event`와 `daily_review`를 보존하고 별도 미수금 도메인을 확장했습니다.
3. **업무 흐름과 완료 조건을 먼저 정했습니다.** 청구·입금 등록 → 매칭 후보 → 사용자 확정 → 잔액 조회를 중심으로 화면과 API를 연결했습니다. 금액 계산은 Java/DB가 담당하고, 후보 생성이 거래 확정을 의미하지 않도록 했습니다.
4. **총괄이 기능별로 작업을 배분했습니다.** 인증, 청구·입금, 매칭·확정·취소, 이용량, 모바일 순서로 확장했습니다. 독립적인 작업은 병렬로 진행하고, API·도메인 설계가 필요한 화면 작업은 선행 결과를 받은 뒤 연결했습니다. 동시 작업은 수정 파일이 겹치지 않도록 나눴습니다.
5. **구현 결과를 별도 에이전트가 검토했습니다.** 정상 흐름뿐 아니라 중복 요청, 동시 확정, 응답 유실, 취소와 화면 전환을 점검했습니다. 발견한 문제는 개발 작업으로 돌려보내 수정하고 관련 검증을 다시 실행했습니다.
6. **실행 근거를 남기고 다음 단계로 진행했습니다.** 테스트 결과, 실제 브라우저 화면, 재현 스크립트와 남은 한계를 기록했습니다. 기능별 변경은 커밋으로 남기고, 공통 업무 규칙은 `AGENTS.md`, 진행 상태는 작업 문서로 유지했습니다.

조사 내용은 고객과 기능의 가설을 정하는 데 활용했습니다. 실제 고객 수요나 유입 성과를 검증한 것으로 표현하지 않았습니다. 이후 제가 FREE 미수금 MVP와 포트폴리오 완성을 우선하도록 범위를 조정했고, 총괄이 그 결정에 맞춰 개발 순서를 갱신했습니다.

### 검토가 실제 수정으로 이어진 사례

**저장은 완료됐지만 응답을 받지 못한 경우, 재시도가 중복 입금을 만들 수 있었습니다.** 기본 화면 검토에서 공백만 수정해도 같은 내용의 요청 키가 바뀌는 문제가 발견됐습니다. 정규화한 입력을 기준으로 키를 유지하도록 수정했습니다. 실제 DB 저장 뒤 응답을 503으로 바꾼 상황을 재현하고, 공백 수정 후 같은 키로 재시도해 입금이 한 건만 남는지 확인했습니다.

입금 연결에서는 **이전 조회의 늦은 응답이 새 후보를 덮거나, 취소 중 화면 이동으로 재요청 정보가 사라지는 상황**도 검토했습니다. 조회·탐색 상태와 요청 키 보관 방식을 수정하고, 지연 응답 및 화면 전환 시나리오를 다시 실행했습니다. 실제 서버 검증과 응답을 제어한 화면 검증은 근거를 구분해 기록했습니다.

이 과정에서 제가 맡은 역할은 문제 정의, 업무 제약과 완료 기준 설정, 역할 구성 및 우선순위 조정이었습니다. 코드 구현·오류 발견·검증 실행은 에이전트를 활용했습니다. **AI가 작성한 결과물을 기능 단위로 통합하고, 별도 검토와 실행 결과를 거쳐 반영하도록 개발 절차를 구성한 경험**입니다.
