# 차곡 발표를 위한 핵심 코드 학습

작성: 2026-11-03 · 갱신: 2026-11-04. PPT의 설명을 실제 코드와 연결하는 학습 자료다. 학습 확인 범위는 하단 기록을 따른다. 아래 질문에 본인 말로 답하고 확인한 범위를 기록하며, 전체 코드 검토 완료로 확대하지 않는다.

## 먼저 정리할 본인 역할

현재 근거로 말할 수 있는 기여는 서비스 목표·업무 규칙·완료 기준 설정, 총괄과 하위 역할 구성 요청, FREE 우선 및 포트폴리오 중심의 우선순위 조정이다. 구체 DDL·잠금·제품 코드 구현과 초기 검증은 에이전트가 수행했다. 이후 사용자 PC의 전체 테스트와 Hermes 실습은 사용자가 안내에 따라 실행했다. 코드를 이해한 뒤에는 “이 구현의 흐름과 선택 이유를 설명할 수 있다”고 말할 수 있다. 실제로 직접 수정·검증한 경험은 그 작업과 결과가 생긴 뒤 추가한다.

## 1. 합계가 맞는데도 왜 개별 연결이 필요한가

청구 A 60,000원, B 40,000원과 입금 100,000원이 있어도 그 돈이 A와 B를 갚은 것인지 금액만으로 확정할 수 없다. 다른 거래의 입금일 수도 있다. 그래서 날짜별 합계 대사와 청구별 지급 확인을 구분한다.

`business_event`는 예정 현금흐름, `daily_review`는 날짜별 검토다. 신규 invoice/payment 사이의 allocation line은 어떤 입금을 어느 청구에 얼마 배분했는지 기록한다. 후보 생성은 추천 결과를 저장하고, 사용자가 확정해야 배분이 생긴다.

읽을 곳: [ERD](receivables-erd.md), [업무 흐름](PORTFOLIO.md#어떤-문제를-풀었나).

**직접 답하기:** 청구 100,000원에 입금 40,000원이 등록만 됐다면 미수는 얼마인가? 연결 확정 후에는 얼마인가?

확인: 등록만 하면 100,000원, 확정하면 60,000원이다. 미배분 입금과 미수는 서로 다른 지표다.

## 2. 멱등성과 동시성 제어는 무엇이 다른가

멱등성은 같은 명령을 여러 번 보내도 한 번 수행한 결과로 처리하는 것이다. 서버는 저장했는데 응답이 끊긴 경우 같은 `Idempotency-Key`로 재시도한다. 같은 키·같은 내용이면 저장 결과를 반환하고, 같은 키·다른 내용이면 충돌이다.

동시성은 서로 다른 두 요청이 같은 자원을 동시에 사용하는 문제다. 입금 100,000원에 각 70,000원을 배분하는 요청이 각각 다른 키로 들어오면 멱등성만으로는 과배분을 막지 못한다. 부모 행을 잠그고 앞선 요청의 결과가 반영된 잔액을 다시 검사해야 한다.

읽을 곳: [AllocationService](../backend-java/src/main/java/com/smallbiz/reconciliation/receivables/allocation/AllocationService.java)의 `confirm`, `reserve`, `lockParents`, `checkAvailable`.

**직접 답하기:** 두 요청이 동시에 잔액 100,000원을 읽은 후 각각 70,000원을 저장하면 어떤 문제가 생기는가? 잠금은 어디에 있어야 하는가?

확인: 총 140,000원이 배분될 수 있다. 현재 구현은 트랜잭션 안에서 부모 입금·청구를 잠근 뒤 활성 배분을 합산하고 검사한다. 먼저 저장한 요청 뒤 두 번째 요청은 30,000원의 잔액을 보게 되어 거절돼야 한다. 서로 다른 키라도 이 검사가 필요하다.

## 3. 확정 한 번을 코드로 따라가기

신규 미수금은 Controller → Service → JdbcTemplate의 SQL → PostgreSQL이다. 별도 Repository 계층이 있다고 설명하지 않는다.

1. `AllocationController.confirm`이 경로·입력을 서비스에 전달한다.
2. `AllocationService.confirm`이 트랜잭션 안에서 인증·사업체를 확인하고 `reserve`로 명령 키를 확보한다. 저장된 같은 명령이면 기존 응답을 반환한다.
3. `lockAndValidate`가 입금 ID 순서, 청구 ID 순서로 부모를 잠그고 요청 합계와 현재 잔액을 검사한다.
4. 배분 batch·line과 audit를 저장한다. 중간에 실패하면 명령과 배분·감사가 함께 롤백된다.
5. 성공 결과를 반환한다. 후속 현재 상태 조회와 과거 명령의 재생 응답은 구분한다.

**직접 답하기:** 배분 저장은 성공했지만 감사 기록 저장이 실패하면 어떤 데이터가 남아야 하는가?

확인: 같은 트랜잭션이므로 이번 확정의 배분과 명령도 남지 않아야 한다. `lateAuditFailureRollsBackConfirmationAndCancellationAndSameKeysCanRetry` 테스트가 이 실패 경계를 다룬다. [검증 근거](receivables-allocation-review.md)

**추가 질문:** READ_COMMITTED가 잠금 없이 모든 경쟁 요청을 해결해 주는가?

확인: 아니다. 격리 수준과 부모 행 잠금·잔액 재검사는 함께 작동한다. 행 간 배분 합계 상한은 단일 CHECK만으로 보장하지 않는다.

## 4. 취소와 재시도 사례 설명하기

취소는 원본 입금이나 배분 line을 삭제하지 않는다. `AllocationService.cancel`이 사유 있는 cancellation과 audit를 추가한다. `detail`은 취소 존재 여부로 상태와 버전을 파생한다. 미수 계산은 취소된 배분을 제외하므로 잔액이 복원된다. 돈을 환불하는 기능은 아니다.

모바일에서 실제 발견한 문제는 공백만 수정해도 요청 키가 바뀌는 것이었다. 정규화 후 같은 내용인데 새 키를 보내면 서버는 별개 명령으로 볼 수 있다. [Registration.submit](../mobile/src/forms.tsx)과 [CommandKey.forPayload](../mobile/src/commands.ts)의 연결을 따라가 본다.

재현은 “실제 DB 저장 → 첫 응답만 503 → 공백 수정 → 같은 키 재시도 → 입금 1건 확인”이다. 네트워크 오류만 모의로 만드는 것과 실제 저장 후 오류를 만드는 것은 검증하는 위험이 다르다.

**직접 답하기:** 같은 키의 과거 확정 응답이 version 1인데 현재 조회가 취소된 version 2라면 모순인가?

확인: 아니다. 전자는 그 명령의 저장된 결과, 후자는 현재 상태다. 앱은 현재 조회를 구분해 보여줘야 한다.

## 5. AI를 활용한 개발 경험 설명하기

발표 골격:

> 기존 대사 시스템을 청구별 미수금 확인으로 확장하는 목표를 정했습니다. Codex에서 기존 코드·DB·테스트를 함께 분석하고 수정·실행·검증을 이어가도록 했습니다. 총괄 아래 기획·조사·디자인·개발·검토 역할을 구성하고, 금액은 Java에서 계산하며 확정은 사용자가 하도록 업무 규칙을 지정했습니다. 구현과 테스트 실행은 에이전트를 활용했고, 별도 검토에서 발견한 결함을 수정·재검증하는 방식으로 진행했습니다.

여기에 본인이 실제로 설명할 수 있게 된 코드 한 사례를 붙인다. 직접 구현·실행한 비율, 도구 간 성능 비교, 학습하지 않은 기술의 숙련도를 만들어 넣지 않는다.

**직접 답하기:** 독립 AI 검토가 통과하면 출시 준비가 끝났는가?

확인: 아니다. 같은 종류의 오해를 공유할 수 있으므로 코드·재현 근거를 확인해야 한다. 실DB 검증, UI fixture, 브라우저, 실기기는 서로 다른 범위다. 고객 사용성과 보안·운영 검증도 별도로 남아 있다.

## 학습 확인 — 2026-11-03

사용자는 대화에서 등록과 확정의 잔액 차이, 같은 키의 재시도, 다른 키의 동시 배분 위험을 설명했다. 잠금 후 잔액 재검사와 요청 내용 변경 거절은 설명·피드백을 거쳤다. 같은 키로 금액을 바꾼 요청이 거절된 뒤 배분1건·미수6만원이 유지된다고 답했고, 실제 축소 금액 테스트의 기대값 allocatedAmount=40/outstandingAmount=60을 직접 선택했다.

에이전트가 그 값을 `AllocationIntegrationTest.idempotentConfirmationNormalizesOrderAndPreservesOriginalSnapshotAfterCancellation`의 충돌 응답 직후 잔액 assertion으로 반영하고 실행했다. 최초 실행은 Gradle 네트워크 초기화 제한, 다음 실행은 PostgreSQL 중단으로 ApplicationContext 초기화 실패였다. 실행 권한 조정과 기존 PG17 데이터 디렉터리 재기동 후 전용 reconciliation_test에서 해당 테스트1개 통과(실패·오류·스킵0, BUILD SUCCESSFUL17s). 전체 테스트는 재실행하지 않았다.

사용자 기여는 시나리오 판단과 기대값 결정이며 파일 편집·명령 실행은 에이전트가 수행했다. 코드 전체 이해·직접 실행 완료로 간주하지 않는다. 다음 확인은 테스트의 준비·실행·검증 부분을 본인이 구분하고 해당 assertion을 충돌 직후에 두는 이유를 설명하는 것이다.

### 입금 쪽 잔액 검증 추가

사용자가 `assertMoney(paymentBalance(owner, p1), "unallocatedAmount", "60");`를 채팅에 직접 작성했다. 메서드·필드·기대값과 형식은 사전 안내를 받았으며, 에이전트가 청구 잔액 검사 아래에 반영했다. 사용자는 첫 확정 직후 검사는 정상 반영, 충돌 직후 검사는 실패 요청의 데이터 변경 여부를 확인한다는 차이를 설명했다.

동일 테스트를 전용 reconciliation_test에서 재실행해 1개 통과·실패/오류/스킵0, BUILD SUCCESSFUL17s를 확인했다. 실행 로그는 `/workspace/.local/run/learning-payment-balance-nov03.log`다. 이번 연습의 사용자 기여는 기대값 판단·검증 위치 설명·안내에 따른 assertion 한 줄 작성이며, 전체 테스트 설계나 직접 실행 경험으로 표현하지 않는다. 전체 회귀와 금융 기능 코드는 이번에 변경·검증하지 않았다.

## Hermes 로컬 도구 실습 — 2026-11-03

### 사용자 PC에서 확인된 내용

사용자가 Windows/WSL2 Ubuntu에 Hermes Agent v0.22.6(local f0d94882e89a)을 Git 방식으로 설치했다. CLI Python3.14.9와 OpenAI Codex 인증 경로·gpt-6.1-sol 설정을 확인하고 실제 응답을 받았다. systemd 사용자 버스 오류는 Gateway 포그라운드 실행으로 우회했다. 초기 command not found는 shell 경로 재적용 후 해결됐다. 안내했던 --list-tools는 이 버전 parser에서 지원하지 않아 제거했다.

에이전트가 제공한 plugin.yaml/__init__.py 예제를 사용자가 ~/.hermes/plugins/chagok-demo에 작성하고 활성화했다. Plugin Doctor는 manifest·import·등록 검사를 통과해1tool/0hook을 보고했다. 새 세션은 --toolsets chagok_demo --max-turns5로 실행하도록 안내했다. 사용자 콘솔 화면에서 도구 상세 조회와 chagok_receivables_demo 호출 표시, 합성 청구100000/배분40000/미수60000 및 DEMO 식별자를 포함한 답변을 확인했다. 2026-11-04는 NO_DATA이며 금액0·미입금·미업로드로 단정하지 않는 답변을 사용자가 공유했다.

이후 사용자가 안내에 따라 DATA 응답에 counterparty_name=샘플상점 필드를 추가했다. Doctor와 Python lookup 직접 실행을 통과했다고 보고했다. Gateway 재시작·새 세션 후 사용자 공유 화면에서 조회 도구 호출과 샘플상점·청구100000·미수60000·원본 식별자가 포함된 응답을 확인했다.

### 역할과 검증 한계

설치·명령 실행·예제 파일 작성·필드 수정은 사용자가 PC에서 수행했고 코드 예제·수정 위치·검사 명령은 에이전트가 제공했다. 따라서 안내에 따른 도구 확장·직접 실행 경험으로 기록하며, 코어를 독자 설계·수정했다고 표현하지 않는다. 증거는 대화에 공유된 로그·스크린샷이며 총괄이 사용자 PC나 원시 모델 전송 로그에 직접 접속한 검증은 아니다. 개인 인증 파일과 토큰은 저장소에 보관하지 않는다.

당시 도구는 고정 합성 자료만 반환했다. 실제 Java 조회 API·DB·PRO 기능·금액 계산의 모델 호출 검증 완료를 뜻하지 않는다. 화면의 도구 상세 조회와 실제 도구 호출을 합쳐 금융 처리2회라고 해석하지 않는다. 다음 단계는 로컬 Java/PostgreSQL 실행 환경 확인, 기존 인증된 조회 API와의 연결 및 호출 근거 보존이다. 플러그인 소스의 버전 관리도 후속으로 남아 있다.

## WSL 백엔드 실행·전체 테스트 — 2026-11-04

사용자가 개인 PC의 Ubuntu26.04 WSL에 OpenJDK21.0.12.1과 공식 PGDG PostgreSQL17.11을 설치했다. reconciliation_dev/chagok_dev와 reconciliation_test/chagok_test를 분리하고 서로 다른 DB CONNECT 권한이 모두 false임을 SQL로 확인했다. 비밀번호는 터미널의 숨김 입력을 사용하고 대화·저장소에 기록하지 않았다.

Windows 마운트 경로 빌드에서 보고서 쓰기 Operation not permitted가 발생했다. Git의 권한·CRLF 차이를 제외한 diff stat 출력이 없음을 확인한 뒤 Windows 원본을 남겨두고 ~/projects에 별도 복제했다. 사용자가 공유한 시작 로그에서 새 개발 DB 연결, Flyway V1~V13 적용, Tomcat8080 및 Started ReconciliationApplication을 확인했다. 이어 전용 테스트 계정/DB로 전체 테스트 명령을 직접 실행해 BUILD SUCCESSFUL을 보고했고 XML 합산 결과186/실패0/오류0/스킵0을 공유했다.

이 결과는 사용자 PC 실행 로그·보고에 근거하며 총괄이 같은 PC에서 명령을 대신 실행한 것은 아니다. 기존 클라우드 검증과 구분한다. 이 시점에는 실제 Java 조회 API 연결이 후속이었다. 같은 날 아래 실습에서 실제 GET과 모델 도구 호출을 추가로 확인했다.

## 실제 Java API를 읽는 Hermes 도구 — 2026-11-04

사용자가 별도 합성 계정을 만들고 청구 100,000원·입금 40,000원·확정 배분 40,000원을 수동 실습 스크립트로 준비했다. AI가 거래를 생성·확정한 것이 아니다. 세션은 사용자 홈의 비공개 파일에 두고 소스·로그에 토큰을 노출하지 않았다.

`chagok_receivables_summary(as_of="2026-11-04")`는 고정 localhost의 인증된 Java summary GET만 호출한다. 직접 함수 실행에서 DATA, CURRENT_LEDGER, 미수 60,000원과 근거 API 경로를 확인했다. 이후 사용자가 Hermes의 실제 도구 실행 표시를 확인했고, 반환된 금액·건수·조회 범위를 설명한 답변을 공유했다. 답변은 특정 날짜의 거래나 과거 잔액·개별 원본까지 확인했다고 주장하지 않았다.

추가로 존재하지 않는 날짜(2026-02-30)를 입력해 INVALID_DATE를 확인했다. Python unittest.mock으로 HTTP 401과 연결 실패를 발생시켜 AUTH_REQUIRED / UPSTREAM_UNAVAILABLE를 확인했다. 이 두 검사는 실제 세션 만료·서버 중단 재현이 아닌 모의 오류 검사다. 실제 모델 호출은 정상 조회 경로에서 확인했고, 모든 실패 상황을 모델로 재검증한 것은 아니다.

확인한 흐름: 사용자 질문 → Hermes → Python GET 도구 → 인증된 Java API → PostgreSQL → 서버 금액 기반 설명. 코드 예제·검사 명령은 에이전트가 제공했고 사용자가 자신의 PC에서 적용·실행했다. 총괄은 공유된 출력과 사용자 확인을 근거로 기록했다. 클라우드 단위 10개와 사용자 PC의 날짜·오류 검사는 별도다.

제품 FREE/PRO 권한 경계는 변경하지 않았다. 로컬 실습 세션 자체가 읽기 전용 권한인 것은 아니며 플러그인 코드가 GET으로 제한한다. Hermes 턴 제한은 내부 재시도까지 포함한 엄격한 API 요청 수·비용 상한 검증이 아니다. Docker·공개 배포는 보류했다.

### 발표에서 설명할 수 있는 사례

> AI 에이전트에게 코드 작성만 맡기지 않고, 금액 계산은 Java에서 하고 확정은 사람이 하도록 기준을 정했습니다. 개인 PC에서 개발·테스트 DB를 분리하고 전체 테스트 186개를 실행했습니다. 이후 Hermes에 날짜만 입력받는 조회 도구를 연결해, Java가 반환한 미수 6만 원과 조회 근거가 답변에 반영되는 것을 확인했습니다. 자료가 없는 경우와 인증·연결 실패를 구분해야 한다는 점도 실습했습니다.

다음 설명 연습: 요청 키가 같아도 내용이 달라지면 왜 거절하는지, 다른 키의 동시 요청에는 왜 잠금이 필요한지, 현재 요약을 과거 잔액으로 설명하면 왜 틀리는지 코드와 연결해서 말한다.
