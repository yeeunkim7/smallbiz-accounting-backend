# 개발 방향 갱신: FREE 미수금·입금 확인 MVP

갱신: 2026-11-01, Asia/Seoul. 이번 단계는 **P0 검증과 계획·규칙 준비**다. 기존 기능을 폐기하지 않으며 신규 DB 마이그레이션·인증 코드·Expo 앱 구현은 아직 하지 않았다.

## 1. 현재 상태와 목표 비교

| 구분 | 현재 확인 | 처리 방향 |
| --- | --- | --- |
| 이미 구현 | 거래처 CRUD, 업무/은행 CSV 검증·중복 방지·원본 추적, 일/월 합계, 검토 상태와 동시 수정 방지 | 기존 API·V1~V7·원본 보존 |
| 이미 구현 | 읽기 전용 하루 요약·기간/방향 원본·관련 업로드, 명시적 AI 도구 4개, 모델 요청 최대 5회, 웹 화면 | PRO 확장 자산으로 보존. 현재 서비스 등급 권한은 없음 |
| 수정 필요 | 전역 거래처 코드·파일 해시·원천 ID, 날짜만으로 식별되는 검토 | 새 사용자/사업체 데이터에 그대로 적용하지 않음. 검증된 소유권 없이는 기존 자료를 새 계정에 연결하지 않음 |
| 수정 필요 | 현재 AI API에 계정·등급 가드 없음 | FREE 출시 전에 기존 AI 경로까지 서버 인증/PRO 권한/운영 kill-switch로 보호 |
| 새 개발 | 청구·지급기한, 입금 잔액, 규칙 후보, 다대다 배분 확정·취소·감사 | 신규 미수금 도메인과 트랜잭션. 기존 현금흐름 이벤트와 별도 |
| 새 개발 | 계정/사업체 격리, 서버 등급, 성공 실행 월별 사용량 | 기능 접근과 한도를 서버가 판단, 재요청·동시성 보장 |
| 새 개발 | React Native + Expo + TypeScript | iOS/Android 공통 모바일 앱. 기존 웹 교체 없이 같은 새 API 사용 |

기존 `business_event`의 CHARGE_EXPECTED/SETTLEMENT_EXPECTED/REFUND_EXPECTED는 현금 예정 데이터다. 고객에게 청구한 채권·지급기한·확정된 입금 배분·남은 채권을 뜻하지 않는다. `daily_review.REVIEWED`도 청구 건의 입금 확정을 뜻하지 않는다. **날짜별 합계 일치를 채권 소멸 또는 거래 매칭으로 재해석하지 않는다.**

세부 근거: [도메인·DB 계획](receivables-domain-plan.md). 기존 AI 검증 이력은 [AI 작업 기록](AI_REVIEW_WORK.md)에 유지한다.

## 2. FREE MVP 최소 범위

우선 과업: 거래처에 청구한 금액 중 무엇이 입금됐고 무엇이 아직 남았는지 확인한다. `입금 누락`은 통장 내역이 없다는 사실만으로 확정하지 않는다. UI는 `미수금`·`연체`·`확인 필요`로 설명한다.

- 로그인한 사용자와 소유 사업체 1개, 사업체별 거래처·청구·입금·원본·감사 접근 제어.
- 원화 정수 금액. 청구일·지급기한·거래처·청구금액을 직접 입력. 은행 입금은 직접 입력 및 기존 지원 CSV의 검증 코드를 재사용하는 **새 tenant 소유 import**로 등록.
- 금액·날짜·거래처 조건으로 제한된 후보 생성. 이름/금액이 같다는 이유로 자동 확정하지 않음. 후보 부재도 미입금을 확정하지 않음.
- 한 청구에 여러 입금(부분 입금), 한 입금을 여러 청구에 나누는 배분(묶음 입금)을 사용자 검토 후 확정. 자동 부분집합 탐색·복잡한 자동 조합은 후순위.
- 청구 잔액/지급기한 초과 잔액과 배분되지 않은 입금을 별도로 표시. 초과 입금을 음수 미수금으로 만들지 않음.
- 잘못된 확정은 취소 이벤트와 이유를 남기고 다시 배분. 확정된 이력을 덮어쓰거나 지우지 않음.
- 월별 성공 대사 사용량, 실패/중복 재요청/동시 요청 처리, 파일 크기·행 수 제한을 서버에서 적용.
- 홈/등록/후보 검토/미수금 상세/계정·이용량 5개 모바일 흐름. 합성 샘플은 실데이터와 분리한 로컬 읽기 전용 체험으로 시작.
- **FREE에서 모델 호출 0회**: AI 버튼 없음에 더해 서버에서 FREE/STANDARD의 새 경로·기존 AI 경로·직접 호출·백그라운드 작업을 차단. API 키가 있더라도 AI 클라이언트가 호출되지 않는 테스트 필수.

자동 알림 발송, 세금계산서 발행/조회, 은행 인증 연결, 돈 이동, 다통화, 실제 결제/구독은 첫 MVP에서 제외한다. 청구 대체·수정·분쟁 처리를 위한 상업 회계 원장을 완성했다고 주장하지 않는다.

## 3. 등급·한도: 설정 가능한 가설

| 등급 | 이번 방향 | 미확정 가설 |
| --- | --- | --- |
| FREE | 규칙 기반 확인·수동 확정·기본 미수/연체 | 월 10회 **성공 대사** |
| STANDARD | 거래량 확대·미수금 관리 확장 | 월 9,900원 |
| PRO | 고급 관리·보고서·읽기 전용 AI | 월 약 30,000원 |

가격·무료 횟수는 문서의 가설이다. 금액 리터럴을 엔티티/비즈니스 분기/화면에 박지 않는다. 서버 정책 설정 또는 버전 있는 plan policy를 조회하며 앱은 응답을 표시한다. 유료 결제 연동 전 임의 등급 상승 API를 공개하지 않는다. 월별 실적 UI는 서버의 완료된 실행을 기준으로 한다.

제안하는 실행 정의:

1. 파일 가져오기·결과 새로고침·후보 확정/취소는 대사 실행과 분리한다. 사용자가 선택한 범위의 규칙 후보 생성 작업이 성공하고 결과가 저장될 때 한 번 차감한다.
2. `(사업체, 작업 종류, Idempotency-Key)`와 요청 payload hash로 같은 요청을 식별한다. 같은 키/다른 payload는 409, 같은 완료 작업 재요청은 같은 결과를 반환하고 추가 차감하지 않는다.
3. 월 한도 행을 잠그고 `성공 수 + 진행 중 예약 < limit`을 확인해 예약한다. 실패는 예약만 해제하며 완료 수를 늘리지 않는다. 성공 결과 저장·예약 해제·성공 수 증가는 같은 DB 트랜잭션으로 처리한다.
4. 작업 기한·lease/fencing token을 두어 중단된 예약을 회수하고 늦은 worker의 중복 성공 기록을 막는다. 한도 오류는 명확한 서버 오류로 앱에 전달한다.
5. **기준 월 제안:** 실행 승인 시점의 사업체 시간대(초기 Asia/Seoul) 월을 작업에 고정하고 그 월에 성공을 반영한다. 월말을 넘긴 완료·같은 키 재요청도 원래 작업 월을 따른다. 이는 구현 전 확정할 제품 계약이며 날짜를 기기 시계에서 믿지 않는다.

파일 한도 제안: 기존 파서의 5MiB/10,000행 안전 상한을 재사용하되 FREE 미수금 import는 정책으로 **1MiB/1,000행/파일**부터 부하·메모리 테스트한다. 현재 시행된 한도가 아니며 실패·취소 업로드는 월 성공 대사를 차감하지 않는다. multipart 여유, 문자열/금액/날짜 검증, 계정 저장량·요청 속도 제한도 별도로 둔다.

| 후속 | STANDARD/PRO 보고서·AI·실제 구독 | 수요·운영 비용 검증 후 별도 기능 단위 개발 |

**다음 개발 작업 하나:** 서버의 계정·사업체 인증 경계와 plan entitlement를 먼저 구현하고 기존 AI endpoint까지 보호한다. 아직 공개 서비스가 아니므로 검증된 소유권 없는 legacy 데이터는 기존 개발 자료로 분리한다. 인증 공급자·비밀번호 복구/메일 비용·계정 삭제 방식을 짧은 ADR로 정한 뒤 최소 스키마/API를 추가한다. 기존 API의 응답 계약은 보존하되 접근 제어 도입은 명시적 보안 변경으로 기록한다.

Expo 프로젝트는 이후 `mobile/`에 추가하고 backend와 분리한다. Android/iOS 별도 앱 코드와 앱인토스 코드는 만들지 않는다. EAS·서명·스토어 계정·심사 정책은 실제 진행 전 공식 자료와 비용을 확인한다. 이번 단계에서 앱스토어 빌드나 실기기 동작을 확인한 것으로 표시하지 않는다.

## 5. 금액·보안 테스트 계획

- 청구 100,000 / 입금 40,000+60,000 → 잔액 0; 입금 100,000을 두 청구 30,000+70,000에 배분 → 두 잔액 0.
- 청구액·입금액 초과 배분 거절, 음수/0/overflow 거절, 미배분 입금 별도 표시. 날짜 불일치·동명이인·동액 후보는 사용자 확인 상태.
- 지급기한 당일 vs 다음 날(사업체 시간대)·부분 입금의 연체 잔액, 취소 후 복원, 수정/취소 중 동시 요청·낡은 version 충돌.
- 청구·입금 행의 정해진 잠금 순서, DB 제약과 최종 재검증으로 이중 배분 방지. 후보 점수는 금액 확정의 근거가 아님.
- 파일/원본 ID 중복의 tenant 범위, 다른 계정 ID 추측·원본 조회·배분·usage 호출 거부. 신규 tenant와 legacy bank 행을 자동 연결하지 않음.
- 10번째 성공·11번째 거절, 실패 0차감, 같은 요청 1회, 다른 payload 동일 키 409, 마지막 1칸 경쟁·worker 장애·재시도·월말 처리.
- 실제 키가 서버에 있어도 FREE/STANDARD/미인증의 AI 접근에서 mock AI invocation=0. PRO도 운영 kill-switch·5요청/출력/시간 예산 적용.
- 기존 회귀는 테스트 DB만 사용하고 개발 DB 행 수와 migration history를 전후 비교. 개인 금융 자료 대신 합성 데이터만 사용.

## 6. P0 검증 근거

새 환경에서 실제 확인한 도구·스키마·테스트 결과는 아래 완료 기록에 추가한다. 이전 결과를 이번 실행 결과로 대체하지 않는다. 관련 문서: [시장 조사/빈틈](receivables-market-plan.md), [모바일 UX 계획](receivables-mobile-plan.md).

### 이번 P0 실제 완료 기록

- 실제 경로 `/workspace/smallbiz-accounting-backend`, HEAD `580adf5d496b5c59093d3075548dd7897eed8c23`. 기존 README/build.gradle/index.html의 tracked 변경 및 AI 코드·문서·캡처의 untracked 작업을 확인하고 보존했다. 초기 상태 기록: `/workspace/.local/receivables-p0-start-status.txt`. reset/삭제/자동 commit·push 없음.
- JDK/javac21.0.12.1, PostgreSQL17.11. 기존 pgdata를 재시작했으며 개발·테스트 DB가 분리돼 있고 두 DB 모두 FlywayV1~V7 성공이다. 새 migration은 적용하지 않았다.
- `source /workspace/.local/env.sh` 후 backend-java에서 `bash gradlew --offline --no-daemon --project-cache-dir /workspace/.local/gradle-project test --rerun-tasks` 실행. **88개 성공, 실패/오류/스킵0**, XML12개, exit0, BUILD SUCCESSFUL12s. 로그 `/workspace/.local/run/receivables-p0-tests.log`. 실제 AI 키는 기존 Gradle test 보호로 상속되지 않는다.
- 개발 DB 주요 행 수 전후 동일: vendor1/business_event1/bank_transaction1/upload_file2. 이는 행 수 보존 확인이며 전체 데이터 바이트 동일성 검증은 아니다.
- 변경은 계획 문서·AGENTS·README/작업 기록뿐이다. 기능 소스·테스트·DB 원본은 수정하지 않았다. 신규 금액 배분, 권한, quota, 모바일 화면은 아직 구현·검증 전이다.
- 시장 신규 필수 후보 볼타·대사노트·경리나라는 공식 근거 확인이 남아 있다. 기존자료 재분류와 이번 웹403 확인을 신규 조사 완료로 과장하지 않는다.

## 첫 기능 단위 진행: 인증·사업체·AI 경계

P0 이후 계정·사업체·세션을 위한 V8과 서버 권한 경계를 구현했다. 기존 전역 금융 API는 기본 거부하며, legacy-dev 프로파일과 명시적 옵션을 함께 사용한 익명 개발 fixture만 보존한다. FREE/STANDARD와 미인증 사용자는 모델을 호출할 수 없고, PRO도 tenant 전용 도구 완성 전까지 차단한다.

[구현 API·실행 안내](AUTH_FOUNDATION.md) · [독립 검토](auth-security-review.md). 전체 104개 테스트가 통과했다. 다음 기능 단위는 tenant 소유 거래처·청구·입금 직접 등록이다. 배분·미수 계산·quota·Expo와 운영 계정 보호 작업은 남아 있다. 이 기록은 앞선 P0 당시 기능 소스 미변경 기록과 구분한다.

## 등록 단계 완료

사업체별 거래처·청구·입금 직접 등록 및 목록/상세 API와 V9를 추가했다. 전체118개 테스트 성공, 금액·날짜·테넌트 격리·동시 idempotency 검증을 포함한다. 아직 배분·미수/연체·사용량은 계산하지 않는다. 다음 기능 단위는 수동 배분 확정·취소와 정확한 미수/연체 계산이다.

## 수동 배분·미수 계산 단계 완료

부분·묶음 입금의 수동 확정, 사유 있는 취소, 원본 보존·감사 이력과 현재 미수/연체/미할당액 조회를 구현했다. 전체 135개 테스트가 통과했다. [배분 계약](RECEIVABLES_ALLOCATION.md). 자동 후보, CSV 수금 가져오기, 월 성공 실행 사용량, Expo와 공개 운영 준비는 남아 있다.

## 규칙 후보 생성 단계 완료

청구·입금의 현재 가용액과 이름·날짜 근거로 규칙 후보를 생성하고 불변 실행 결과를 저장한다. 자동 배분하지 않으며 후보 0건을 입금 누락으로 확정하지 않는다. 전체149개 테스트 통과, V11 및 [API 계약](RECEIVABLES_MATCHING.md)을 추가했다. 월별 성공 실행 quota는 아직 적용 전이므로 공개 FREE 서비스가 준비됐다고 표시하지 않는다. 다음 기능 단위는 tenant 소유 은행 CSV 가져오기와 원본 추적이며, 이후 저장된 matching run의 성공 사용량을 서버에서 제한한다.
