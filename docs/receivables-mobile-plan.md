# FREE 미수금서비스 모바일 UX 계획

상태: 구현 전 UX·제품 계획. 기준일 2026-11-01. 이번 P0는 실제 UI 코드나 프로젝트를 추가하지 않는다. 디자인 시안 작성과 실제 렌더링 검증은 실행하지 않았다.

## 목적과 제품 경계

소사업자가 이동 중 고객별 청구, 입금, 미수 잔액과 연체를 빠르게 기록하고 확인하는 모바일 앱을 설계한다. 제품 흐름은 `청구 등록 → 입금 등록 → 후보 검토 → 사람이 확정 → 미수 확인`이다. 후보는 제안이며 자동 매칭 확정, 독촉 발송, 회계·세무 서비스 대체를 의미하지 않는다. 기존 일별 합계가 같다는 사실과 각 거래가 개별로 연결됐다는 사실을 분리해 표시한다.

앱은 React Native, Expo, TypeScript로 iOS와 Android를 함께 지원한다. 개발은 Windows 환경을 포함하며 iPhone 실기기 확인은 필요 시 EAS Build를 배포 검증 게이트로 삼는다. 현재 저장소는 Java 백엔드와 정적 웹으로 모바일 앱이 없다. 웹 클라이언트가 추가되면 모바일과 같은 API를 사용하도록 API 계약·권한·검증을 클라이언트와 독립적으로 설계한다.

FREE의 AI 호출은 0회다. 정상 완료 10회/월은 제품 가설일 뿐 확정 한도나 가격이 아니다. 실제 계정별 사용량과 한도 판정은 서버가 담당하며 앱에 가격·월 한도 상수를 두지 않는다. 서버가 확정한 사용량/한도 상태를 표시할 수 있게 API 계약을 정한다. 총괄 계획의 후보 생성 run 정상 완료만 차감하는 정책을 따른다. 실패·중단은 성공 횟수를 늘리지 않고, 수동 확정·취소·조회·파일 등록은 차감하지 않는다. 월은 실행 승인 시점의 사업체 월로 고정하는 제안이며 상세 계약은 총괄 계획 3절을 따른다.

## 정보 구조와 첫 화면

하단 탭은 `홈`, `청구·입금`, `확인 필요`, `계정`으로 구성한다. 상세 화면은 스택 탐색으로 열고, 홈에는 고정 입력 버튼 `청구 추가`와 `입금 추가`를 둔다. 목록에서 작성 흐름으로 진입해도 입력 자료를 잃지 않도록 초안 상태를 유지한다.

홈의 첫 화면은 한 번에 다음 우선순위를 보여준다.

1. 상단 날짜 문맥과 계정/샘플 작업공간 표시.
2. `미수 잔액`, `연체 잔액·건수`, `확인 필요 건수`를 읽기 쉬운 요약으로 제시.
3. 가장 먼저 처리할 확인 필요 항목과 기한이 지난 청구를 표시.
4. 눈에 띄는 청구·입금 추가 행동.
5. 최근 활동은 보조 영역에 두고, 합계 숫자가 개별 매칭 완료를 뜻하지 않는다는 설명을 필요한 위치에 둔다.

실자료가 없을 때 숫자를 0으로 위장하지 않는다. `아직 등록된 청구가 없어요`와 첫 청구 추가 행동을 보여주고, 체험은 `샘플 작업공간` 진입으로 분리한다. 샘플은 합성 데이터 전용 tenant 또는 기기 로컬의 읽기 전용 체험 데이터로 제공한다. 실제 고객 tenant·검색·내보내기에 섞이지 않고, 실제 사용량/쿼터를 소비하지 않아야 한다. 서버 tenant 분리가 구현되지 않았다면 로컬 체험만 노출한다. 샘플 작업공간임을 상시 표시하고 실제 데이터로 변환하거나 복사하는 기능은 P0에 포함하지 않는다.

## 다섯 화면

1. **홈:** 미수·연체·확인 필요 요약, 우선 처리 항목, 청구/입금 추가, 최근 활동, 자료 없음 상태. 합계는 범위와 기준일을 함께 보여준다.
2. **청구·입금 등록:** 직접 입력이 기본 경로. 고객, 청구일, 금액, 기한, 메모를 입력하고 입금은 입금일, 금액, 입금자/메모를 입력한다. CSV는 보조 가져오기 경로이며 미리보기·열 확인·오류 행 설명·확인 후 반영 단계를 거친다. 합성 샘플은 가져오기 파일과 별도 체험 영역에만 둔다.
3. **후보 검토·확정:** 연결 후보와 근거(고객/입금자, 금액, 날짜 등 서버가 제공하는 정보)를 나란히 확인하고 `확정`, `다른 후보 선택`, `보류`를 제공한다. 자동 확정 금지. 금액이나 이름의 유사도만으로 사실처럼 단정하지 않는다. 일별 총액이 일치해도 개별 연결을 완료로 표시하지 않는다.
4. **미수 상세:** 청구 원금, 기한, 누적 입금, 잔액, 상태와 할당된 입금 내역을 표시한다. 한 번의 입금을 여러 청구에 나누는 부분 할당, 여러 입금을 한 청구에 모으는 묶음 할당을 지원한다. 할당 전후 잔액과 전체 금액 검증을 보여준다. 확정된 할당은 감사 가능한 취소 동작으로 되돌리고 취소 이유/영향을 확인한다. 삭제와 취소를 혼동시키지 않는다.
5. **계정·이용량:** 계정/사업장, 현재 플랜 `FREE`, 서버가 반환한 사용량과 기준 기간, 개인정보·도움말 링크를 둔다. FREE AI 사용량은 0회로 설명한다. 월 10회는 가설로 문서에만 남기고 화면 또는 클라이언트 로직에 확정 한도로 표시하지 않는다. 가격·한도는 서버 정책으로 확인 전 표시하지 않는다.

## 상태와 문구

- **금액:** 원화는 `1,234,567원`, 음수는 `−12,345원`; 금액은 우측 정렬, 숫자는 고정 폭 숫자 스타일을 사용한다. 합계·잔액의 기준일과 포함 범위를 붙이고, 서로 다른 의미의 합계를 상계하지 않는다.
- **날짜·기한:** 화면 문장에는 `2026년 11월 1일`, 목록에는 `2026.11.01`처럼 읽기 쉬운 형식으로 통일한다. 기한 상태는 `오늘 기한`, `D-3`, `3일 연체`처럼 날짜 차이를 분명히 한다. 날짜만으로 고객이 독촉을 받았거나 지급을 약속했다고 추정하지 않는다.
- **부분 입금:** `일부 입금 · 잔액 30,000원`과 같이 납부액·남은 금액을 함께 제시한다. 입금이 할당되지 않았다면 청구 상환으로 간주하지 않는다.
- **확인 필요:** 후보 미확정, 초과 입금, 미할당 입금, 금액 불일치 등 실제 서버 상태를 구체 문구로 표시한다. 상태를 색만으로 전달하지 않는다.
- **확정:** 대상 청구/입금과 금액을 확인한 뒤 명시적 확정 액션을 요구한다. 성공 후 연결 관계와 갱신 잔액을 표시하고 되돌릴 수 있는 취소 경로를 제공한다.
- **취소:** 영향받는 청구 잔액·연결 상태를 사전에 보여주고 취소 확인을 받는다. 취소 완료와 실패를 구분하며, 요청 중 중복 제출을 막는다.
- **자료 없음:** `아직 등록된 청구가 없어요`처럼 업무 맥락을 말하고 등록 또는 샘플 체험 행동을 안내한다. 조회 실패를 자료 없음으로 표시하지 않는다.
- **로딩:** 화면 전체를 막기보다 해당 목록·요약 영역에 로딩 표시를 둔다. 입력 폼 초안과 선택 날짜를 유지한다.
- **오류:** 사용자가 취할 다음 행동을 제공하고 재시도 시 입력 내용을 보존한다. 서버 원문, 스택, 내부 식별자나 비밀값은 보여주지 않는다. 네트워크 오류, 검증 오류, 권한/세션 오류를 구분한다.
- **AI:** FREE 업무 흐름에서 AI 호출을 제공하지 않는다. AI 시작 버튼이나 호출 유도는 두지 않는다.

## 시각·접근성 원칙

기존 하루 검토 설계의 절제된 배경/표면/선과 상태 의미를 재사용하되, 네이티브 시스템 글꼴과 safe area를 따른다. 제안 토큰은 구현 시 기기 대비 검증 후 확정한다.

| 토큰 | 초안 값 | 쓰임 |
| --- | --- | --- |
| `color.bg` | `#F5F7F8` | 화면 배경 |
| `color.surface` | `#FFFFFF` | 목록·입력 표면 |
| `color.text` | `#172B2A` | 본문 |
| `color.muted` | `#5D706D` | 보조 정보 |
| `color.border` | `#DDE5E3` | 경계·구분선 |
| `color.primary` | `#086F63` | 주요 행동·선택 |
| `color.success` | `#16634A` | 확정·완료 |
| `color.attention` | `#9A4210` | 연체·검토 필요 |
| `color.error` | `#B42318` | 실패·오류 |
| `space` | 4, 8, 12, 16, 24, 32 | 간격 단위 |

주요 금액은 28–32pt, 화면 제목은 24–28pt, 본문은 16pt 내외로 시작하고 시스템 글자 크기 확대를 지원한다. 모든 터치 대상은 최소 44×44pt로 잡는다. VoiceOver/TalkBack 이름·역할·상태를 제공하고, 포커스 순서와 동적 글자 크기에서 내용이 잘리지 않는지 확인한다. 색상 외에 문구/아이콘/모양으로 상태를 구분하고, 텍스트 대비는 일반 본문 기준 4.5:1 이상을 목표로 실기기 확인한다. 키보드가 입력 중인 필드와 저장 버튼을 가리지 않도록 스크롤/키보드 회피를 적용하고, 날짜·금액 입력에서 로케일 키보드와 붙여넣기를 검토한다. 위험한 확정/취소 버튼은 충분한 간격과 구체적 레이블을 둔다.

## 기술·배포 결정 게이트

- Expo Go는 초기 화면·일반 JS 흐름 탐색에 쓸 수 있지만 네이티브 모듈과 실제 배포 환경을 모두 대표하지 않는다. 필요한 네이티브 기능, 푸시/파일 선택 등 의존성을 먼저 조사하고 지원이 필요한 순간 Development Build로 전환한다. Expo Go만으로 실기기 호환을 완료했다고 판단하지 않는다.
- Windows 개발 환경에서 Android 로컬 개발 흐름을 확인한다. iOS 네이티브 빌드 및 iPhone 실기기 설치 방식은 현재 계정·기기·도구 환경을 확인한 뒤 EAS Build 필요 여부를 결정한다. Apple 서명, 프로비저닝, 기기 등록, 개발자 계정의 실제 요구와 절차는 검증 전 확정하지 않는다.
- EAS, Apple/Google 개발자 계정, 서명, 앱 심사, 스토어 제출에 필요한 비용·계정 요건은 추정하지 않는다. 외부 계정 생성이나 유료 서비스 사용 없이 조사 가능한 항목부터 확인하고, 실제 비용은 공식 요금과 계정 조건을 확인하는 배포 게이트로 남긴다.
- 앱스토어 심사 기준, 개인정보/데이터 정책, 금융 데이터 처리 고지·보존·삭제 요건은 검증되지 않았다. 배포 전에 플랫폼 정책과 서비스 데이터 처리 방침을 확인해야 한다. 앱스토어 구독과 인앱 결제는 현재 범위에서 제외한다.
- 모바일과 향후 웹이 공유할 API는 서버 권한 검사, 입력 검증, idempotency/중복 제출 처리, 상태 전이, 페이지네이션, 날짜·통화 의미를 명세한다. 클라이언트 UI 상태를 서버 확정 상태로 가장하지 않는다.

## 후속 구현 단계 완료 기준

1. **API·데이터 계약:** 청구/입금 CRUD, 후보 조회, 수동 확정·취소, 부분/묶음 할당, 서버 사용량 응답이 명세되고 동일 API를 웹에서도 사용할 수 있다. 합계 일치와 개별 매칭 상태는 별도 필드·문구로 유지한다.
2. **앱 골격:** Expo TypeScript 프로젝트가 Windows에서 설치·실행되고 iOS/Android 공통 다섯 화면의 탐색, safe area, 기본 테마가 동작한다. 필요한 네이티브 모듈과 Expo Go/Development Build 경계가 기록된다.
3. **업무 흐름:** 직접 청구/입금 입력, CSV 미리보기·검증, 후보 보류/확정, 부분·묶음 할당, 취소 후 잔액 갱신이 서버 결과와 일치한다. 자동 확정은 없다.
4. **샘플 격리·FREE:** 합성 샘플은 실자료와 별개 작업공간에서 식별되고 실계정 데이터·검색·내보내기·사용량에 섞이지 않는다. FREE AI 호출은 0회이며 사용량/한도는 서버 반환값만 표시한다.
5. **상태·접근성:** 자료 없음/빈 목록, 로딩, 오류·재시도, 오프라인/세션 만료, 중복 제출, 긴 고객명·큰 금액·연체·부분 입금이 검토된다. 44pt 터치, 화면낭독기, 글자 확대, 대비, 키보드 가림, 세로 화면의 잘림/가로 넘침을 iOS·Android에서 확인한다.
6. **실기기·배포 준비:** Windows 개발 절차와 Android 기기 확인, iPhone 실기기 확인을 실제 수행하고 기록한다. 필요 시 EAS Development Build 서명·설치를 확인한다. 앱 심사 및 데이터 정책 조사, 계정/비용 조건 확인은 완료 전 배포 불가 게이트로 남긴다.
7. **검증 기록:** 실제 렌더 캡처와 기기·OS·빌드·테스트 계정의 비식별 조건을 기록한다. 아직 실행하지 않은 UI/렌더/실기기/스토어 검증을 완료로 표시하지 않는다.

## 이번 단계의 검증 상태

이 문서 작성 단계에서는 신규 외부 연구, 유료 API, 계정 생성, 앱 코드 추가, 디자인 시안 작성, UI 실행, 실제 렌더링 및 기기 검증을 하지 않았다. 따라서 시각 토큰과 화면 구조는 검증 전 제안이며, 앱스토어 심사·데이터 정책과 배포 비용도 미확인 상태다.

## 기능 4a 실제 구현 후 갱신

위 P0 계획을 재사용하여 Expo 코어와 실제 API 연결을 구현했다. 홈·등록·페이지 장부·청구 상세·계정 및 격리된 읽기 전용 샘플은 실제 Chromium에서 검증했다. 후보 검토/확정/취소·CSV 모바일 화면과 iPhone/Android 실기기는 남아 있다. 최종 근거는 [모바일 실행·검증 기록](RECEIVABLES_MOBILE_VALIDATION.md), 구현 경계는 [모바일 코어 결정](RECEIVABLES_MOBILE_CORE.md)을 따른다. 앞선 '미구현' 문장은 P0 작성 당시 기록이다.
